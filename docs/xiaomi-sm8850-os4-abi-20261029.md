### 原厂内核中可能额外存在的接口

未找到提供者的代表例子：`ipc_log_string`（44 次）、`ipc_log_context_create`（43 次）、`qcom_smem_get`（18 次）、`qcom_scm_assign_mem`（13 次），另有原厂 `rust_binder.ko` 的多个 Rust 导出依赖（该模块自身有 71 个尚未定位的符号）。

这些名称在候选 R62 `Module.symvers` 中不存在，亦未被当前采集的 505 个原厂 `.ko` 声明为导出。需要进一步验证原厂内核是否将额外的小米/高通接口内建在 `vmlinux`，或还有启动阶段未采集的模块。**不可假定相同 KMI 就自动存在这些导出。**

### 双版本 zram/zsmalloc（已验证的 CRC 差异）

- `vendor_dlkm/zram.ko`、`node_cache.ko` 要求 `zs_malloc` CRC `0x1804f5bc`，原厂 `vendor_dlkm/zsmalloc.ko` 实际导出也是 `0x1804f5bc`。
- `system_dlkm/zram.ko` 要求 `0x36f39fe1`，原厂 `system_dlkm/zsmalloc.ko` 实际导出也是 `0x36f39fe1`。
- R62 #5 的 `mm/zsmalloc` 导出为 `0x36f39fe1`。

因此原厂**两组内部各自一致**；“2 次 CRC 冲突”指的是 **vendor 侧模块若与候选 R62 的 zsmalloc 交叉组合**。不能将其错误地描述成原厂手机本身已有错误，但也不能混用。

### 模块身份及配置门禁

- 402 个 vendor 模块 `vermagic`：`6.12.69-android16-6-4k ...`。
- 103 个 system 模块 `vermagic`：`6.12.69-android16-6-g43b5ab7e247d-abogki561813157-4k ...`。
- #5 分析内核是故意不同的 `6.12.69-android16-6-os4r62-analysis-4k`。不能通过随意改字符串冒充原厂就认定模块可加载；`CONFIG_MODVERSIONS` 情形下也不可仅凭 vermagic 字符串差异断言一定加载失败。

## 真机 Rust Binder 已加载，但当前处于未启用路径（2026-10-29）

用户在当前原厂系统读取运行态：

```text
[rust_binder] LOADED
rust_binder 462848 0 - Live 0x0000000000000000
build-id=46a149b63b1e0840be67a2149bdc7d289ad8e4a4
```

Build ID 与只读 OEM 快照中的 `system_dlkm/.../rust_binder.ko` 完全一致，证明原厂模块确实已加载，不是仅存在于文件系统。

但 R62 源码 `drivers/android/binder/rust_binder_main.rs` 的模块初始化逻辑明确：

- 当同时存在 C Binder 时读取全局 `binder_use_rust`；
- 若 `binder_use_rust == 0`，先移除该 Rust 模块自己的 trace events，然后直接 `return Ok(Self { _netlink: None })`；
- 只有 `binder_use_rust != 0` 才尝试 `unload_binder()`，随后初始化 Rust Binder netlink、shrinker 和 binderfs。

用户当前 `/proc/bootconfig` 未发现 `binder.impl=rust`；此前已记录的原厂 `/proc/cmdline` 同样没有该参数。因此当前最符合源码和运行态的解释是：

> **OEM rust_binder.ko 被 system_dlkm 加载，但 Binder 主实现仍是 C Binder；Rust 模块处于已加载、未接管 Binder 的闲置状态。**

这进一步降低了 Rust Binder 对功能路径的风险，但不能直接把 OEM `rust_binder.ko` 留给 R62 Image：内核在执行模块 init 之前仍必须完成 ELF 重定位和符号版本解析，OEM 模块的 71 个 Rust crate-hash 符号与 R62 实际名称不同，因此混用仍可能在模块初始化前就加载失败。

当前两个可行方向：
1. **最稳兼容方向**：若未来需要 system_dlkm 模块完整加载成功，则部署与 R62 Image 同源构建、185/185 CRC 已验证匹配的 `rust_binder-R62.ko`，并处理签名/AVB/system_dlkm 打包；
2. **最小 Image-only 方向**：证明小米 second-stage 模块加载脚本允许安全跳过未启用的 `rust_binder.ko`，且跳过不会因 `modules.load` 单项失败导致启动流程失败。

AOSP `modprobe`/libmodprobe 在严格加载 `modules.load` 时，单个列出模块无法加载会使 `LoadListedModules(false/strict)` 返回失败，toolbox `modprobe` 随之退出非零。因此在没有拿到小米具体 init/rc 调用方式前，**不能仅因为 Rust Binder 当前闲置就让 OEM 模块加载失败**。

下一步只读审计小米 `.rc` 中是谁、以何种命令加载 `/system/lib/modules/modules.load`，再决定 Image-only 是否可行。当前仍 `safe_to_flash=false`。

## system_dlkm 加载链已定位（2026-10-29）

真机 `grep` 已确认：

- `/vendor/etc/init/hw/init.qti.kernel.rc:61`：`exec_start gki.modprobe`
- `/vendor/etc/init/hw/init.qti.kernel.rc:251`：`service gki.modprobe /vendor/bin/system_dlkm_modprobe.sh`
- 同一 RC 随后 `start vendor.modprobe`。

AOSP init 的 `exec_start` 语义是：启动既有 service 并暂停同一 action 后续命令，直到该 service 退出；service 本身只有配置 `reboot_on_failure` 时，非零退出才会触发指定 reboot。公开的现代 Qualcomm/Xiaomi `init.qti.kernel.rc` 模板中 `gki.modprobe` 是 `disabled + stdio_to_kmsg + vendor_modprobe seclabel + oneshot`，没有 `reboot_on_failure`。**仍需读取 pandora 真机对应 service 定义确认没有 OEM 额外选项。**

用户上传的精确 OS4 `system_dlkm/modules.load` 已核：

- 第 1 项：`kernel/arch/arm64/geniezone/gzvm.ko`
- 第 47 项：`kernel/drivers/android/binder/rust_binder.ko`
- `modules.dep` 中 `rust_binder.ko:` 无依赖；
- 没有其它 system_dlkm 模块把 `rust_binder.ko` 列为依赖。

公开的 Qualcomm/Xiaomi `system_dlkm_modprobe.sh` 实现会先加载 modules.load 的第一项，随后把其它模块**逐个、后台**调用 modprobe，并在最后 `wait`；脚本注释明确说明这样做是为了“in case one of them fails to init”。在该公开实现中，后续单模块失败不会通过 `wait` 结果显式 `exit 1`，随后脚本 `exit 0`。

因此，**若 pandora OS4 的 `/vendor/bin/system_dlkm_modprobe.sh` 与该现代 QTI/Xiaomi 实现一致**，OEM `rust_binder.ko` 在 R62 Image 下因 crate-hash 符号无法解析而失败，应只导致该闲置 Rust Binder 模块未加载，不会阻断其它 system_dlkm 模块，也不应阻断 early-init。由于当前 Binder 主路径本来就是 C Binder，这会使 Image-only 路线成为现实可行候选。

最后门禁：读取 pandora 真机 `gki.modprobe` service 定义与 `/vendor/bin/system_dlkm_modprobe.sh` 原文；在这两份精确文件确认前，仍不把上述公开实现推断升级为 `safe_to_flash`。

### system_dlkm_modprobe.sh 的精确行为

脚本并不按 `modules.load` 列表顺序加载，而是对含 `modules.load` 的目录执行：

1. `find ${kernel_ver_dir} -name "*.ko"`；
2. 第一个结果单独执行 `modprobe`，失败则只 `continue` 当前目录；
3. 其它结果逐个放入后台 subshell 执行 `modprobe`；
4. `wait` 后不检查单个后台模块的状态；
5. 完成扫描后显式 `exit 0`。

因此，即使 OEM `rust_binder.ko` 在 R62 Image 下因为 Rust crate-hash 符号名不匹配而加载失败，**该单模块失败不会把 gki.modprobe service 变成失败退出，更不会触发 reboot_on_failure**。

用户上传的原厂 system_dlkm 归档原始遍历顺序进一步显示首个 `.ko` 为 `gzvm.ko`，`rust_binder.ko` 紧随其后；但即便首模块失败，精确脚本仍会继续其它目录并最终 `exit 0`。因此 Rust Binder 已从“启动阻断项”降级为“闲置模块可能未加载”的兼容性注意项；当前 Binder 主路径仍为 C Binder。

### 505 个 OEM 模块的 vermagic 后半段与 R62 完全一致

对用户真机只读采集的 505 个 OEM `.ko` 全量读取 `vermagic`：

- 505/505 均存在 vermagic；
- 去掉第一个空格前的 kernel release 后，**505/505 唯一后缀均为**：
  `SMP preempt mod_unload modversions aarch64`
- #7 R62 `rust_binder.ko` 的后缀完全相同。

R62 6.12.69 `kernel/module/version.c::same_magic()` 明确：模块存在 symbol version CRC 时，比较 vermagic 前先跳过首段 kernel release，再比较剩余属性。因此候选 #7 的
`6.12.69-android16-6-os4r62-analysis-4k`
与 OEM 的
`6.12.69-android16-6[-g43...]-4k`
**不会仅因首段 release/localversion 不同而被 MODVERSIONS 模块拒绝**。真正的兼容门禁仍是 CRC/符号名和后半段属性；这些项目已在当前审计中逐项验证。

### 静态兼容性阶段结论

到此为止，纯 R62 Image 的主要静态风险已逐项闭环：

- OEM vmlinux KMI：25,618 次 CRC 匹配，0 冲突；
- 387 个曾未定位符号：387/387 已在真机找到；
- Rust Binder：R62 配套模块 185/185 CRC 匹配；OEM 模块加载失败不阻断 init，且当前未启用 Rust Binder；

- vermagic：505/505 后半段属性与 R62 一致，MODVERSIONS 下首段 release 不作为硬阻断。

### ksuinit 失败不会阻断 Android 原厂 init

镜像中的字符串与当前 KernelSU 官方 `userspace/ksuinit` 实现一致。源码逻辑为：

1. 若内核已存在 KernelSU，则跳过 LKM；
2. 否则尝试读取并加载 `/kernelsu.ko`；
3. `load_module_from_path()` 失败只记录错误，**不会从 init() 返回失败**；
4. 随后无条件删除 loader 自身 `/init`，将 `/init.real` 重新链接为 `/init`；
5. 最终 `execve("/init", ...)` 进入原厂 init。

因此即使旧 LKM 与 R62 不兼容，按该 loader 的正常错误路径，Android 仍会回落到与干净镜像逐字节一致的原厂 init。LKM 失败本身不应成为 bootloop 的必然原因。

### ksuinit 本身具有跨内核 LKM 适配逻辑

当前 ksuinit 不是普通 `insmod`：
- 读取 `/proc/kallsyms`；
- 对 `kernelsu.ko` 的 ELF 未定义符号直接绑定当前内核地址；
- 首次 `init_module` 若从 kmsg 检测到 vermagic mismatch，会把模块 `.modinfo` 中 vermagic 替换成当前内核要求值后重试。

因此其设计本身就是让 bundled LKM 适配不同的 GKI 内核构建，不能仅凭模块原始 vermagic `6.12.76-4k` 判断它在 6.12.69 上必然失败。

### 对 R62 #7 的真实符号存在性检查

直接读取当前 `kernelsu.ko` 的 ELF 符号表得到 **233 个不同未定义符号**；再对 #7 R62 的真实 `vmlinux` 全量 symbol table（按 ksuinit 相同规则去除 `$...` / `.llvm...` 后缀）做匹配：

- 需要的未定义符号：233
- R62 #7 可找到：**233/233**
- 缺失：**0**

因此当前 Root `init_boot_a` 与 R62 #7 配合时，KernelSU LKM **很可能能够继续由 ksuinit 动态绑定并加载**。即使最终因结构/运行语义变化而加载失败，loader 的已确认错误路径仍会回退到原厂 init。

### 对第一轮基线测试的影响

此前生成的 `FASTBOOT-BOOT-ONLY` 镜像不再视为“会被旧 LKM 必然干扰到无法判断”的高风险包，但它也**不是严格意义上的纯 R62 无 Root 基线**：当前 init_boot 很可能会继续成功注入 KernelSU LKM。

因此第一轮测试可分两种：
1. **最低风险启动性测试**：保持当前 init_boot_a 不动，使用 `fastboot boot` 临时启动 R62；目标只回答“R62 + 当前已知启动环境能否启动”，不把 Root 状态作为判断项。
2. **严格纯 R62 基线**：先将活动 `init_boot_a` 临时恢复为已验证干净的 OS4.0.5.0 init_boot，再 `fastboot boot` R62；该步骤会暂时去除 LKM Root，属于持久分区写入，必须有明确恢复步骤后再做。

项目默认先采用方案 1，只有方案 1 成功后才有必要做严格纯净基线。

## 功能编译 #3：定位 Clang 19 逻辑运算优先级错误；#4 修复编译中（2026-10-29）

[功能编译 #3 / Run 40894944005](https://github.com/wekingchen/GKI_KernelSU_SUSFS/actions/runs/40894944005) 在增强失败日志提取后，成功暴露第二处真实编译错误：

```text
fs/proc/task_mmu.c:1443:25:
error: '&&' within '||' [-Werror,-Wlogical-op-parentheses]
```

出错语句来自本项目 R62 专用 `smaps_rollup` 兼容层，而非上游 R62 基线：

```c
if (!vma->vm_file || !SUSFS_IS_INODE_SUS_MAP(file_inode(vma->vm_file)))
```

SUSFS 宏自身展开含 `&&`；Android Clang 19/r536225 在 `-Werror` 下拒绝外层 `||` 与展开后的 `&&` 的无显式括号组合。修复采用逻辑等价且短路语义明确的形式：

```c
if (!(vma->vm_file && SUSFS_IS_INODE_SUS_MAP(file_inode(vma->vm_file))))
```

提交 `4c510308f32917aeaf6e6da6fe385fad9ce449bd` 已修改 `susfs-task-mmu-compat.py`；随后提交 `2574c70d572ace2ab3881dc0ad2e973678842538` 同步预检门禁。

[功能编译 #4 / Run 40896020115](https://github.com/wekingchen/GKI_KernelSU_SUSFS/actions/runs/40896020115) 已进入实际 Image/modules 编译，尚未得出最终结论。
