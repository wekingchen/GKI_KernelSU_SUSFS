# 小米 17 Pro OS4.0.5.0 原厂模块 ABI 实测（2026-10-29）

**状态：部分 GKI KMI 证据积极，但仍存在未解决的厂商符号缺口。禁止用 R62 #5 的 NOFLASH 镜像刷机。**

## 输入（均经本地哈希核验）

- 原厂版本：`OS4.0.5.0.XBLCNXM`，Android 17，`6.12.69-android16-6-g43b5ab7e247d-abogki561813157-4k`。
- 用户从真机只读采集的厂商模块快照 SHA256：`9dddfd787c330220115033b647ac18ed88485fc2eecd359ccd94db66e6e90616`；**仅在用户会话中分析，原始 .ko 不上传 GitHub**。
- 6.12.69 GKI R62 [基线 #5](https://github.com/wekingchen/GKI_KernelSU_SUSFS/actions/runs/40840008157) `Module.symvers` SHA256：`69dc25f5e78bb1b03332c0a8cf0169e239e1efbd51c04a7469aea95430f89b2f`。
- 使用真实 ARM64 ELF 解析器读取模块 `__version_ext_names/__version_ext_crcs`、未定义符号及实际 `__ksymtab` 导出；对涉及的 `zs_malloc` 导出又用 `readelf` / `__crc_zs_malloc` 实物交叉验证。

## 实测数据（引用次数，非去重符号数）

| 项目 | 结果 |
|---|---:|
| 原厂模块 | 505 个：vendor_dlkm 402、system_dlkm 103；ELF 解析失败 0 |
| 使用扩展模块符号版本格式 | 505/505 |
| 与 R62 `vmlinux` 的导出符号 CRC 匹配 | **25,618 次（3,481 个不同符号）** |
| 与 R62 `vmlinux` 的 CRC 冲突 | **0** |
| 引用 R62 其它 GKI 模块导出 | 570 次，其中 **568 匹配、2 冲突** |
| 无法在候选 R62 `Module.symvers` 找到的引用 | 4,232 次 |
| 通过原厂其它 `.ko` 的 `__ksymtab` 找到提供者 | 3,309 次 |
| **仍未找到提供者** | **923 次，387 个不同符号，涉及 165 个模块** |

**重要：** 25,618 次 CRC 对齐只证明相关 `vmlinux` 导出接口保持兼容，不能推断 505 个 OEM 模块均可加载。

### 原厂内核中可能额外存在的接口

未找到提供者的代表例子：`ipc_log_string`（44 次）、`ipc_log_context_create`（43 次）、`qcom_smem_get`（18 次）、`qcom_scm_assign_mem`（13 次），另有原厂 `rust_binder.ko` 的多个 Rust 导出依赖（该模块自身有 71 个尚未定位的符号）。

这些名称在候选 R62 `Module.symvers` 中不存在，亦未被当前采集的 505 个原厂 `.ko` 声明为导出。需要进一步验证原厂内核是否将额外的小米/高通接口内建在 `vmlinux`，或还有启动阶段未采集的模块。**不可假定相同 KMI 就自动存在这些导出。**

### 双版本 zram/zsmalloc（已验证的 CRC 差异）

- `vendor_dlkm/zram.ko`、`node_cache.ko` 要求 `zs_malloc` CRC `0x1804f5bc`，原厂 `vendor_dlkm/zsmalloc.ko` 实际导出也是 `0x1804f5bc`。
- `system_dlkm/zram.ko` 要求 `0x36f39fe1`，原厂 `system_dlkm/zsmalloc.ko` 实际导出也是 `0x36f39fe1`。
- R62 #5 的 `mm/zsmalloc` 导出为 `0x36f39fe1`。

因此原厂**两组内部各自一致**；“2 次 CRC 冲突”指的是 **vendor 侧模块若与候选 R62 的 zsmalloc 交叉组合**。不能将其错误地描述成原厂手机本身已有错误，但也不能混用。

### 模块身份及配置门禁

- 402 个 vendor 模块 `vermagic`：`6.12.69-android16-6-4k ...`。
- 103 个 system 模块 `vermagic`：`6.12.69-android16-6-g43b5ab7e247d-abogki561813157-4k ...`。
- #5 分析内核是故意不同的 `6.12.69-android16-6-os4r62-analysis-4k`。不能通过随意改字符串冒充原厂就认定模块可加载；`CONFIG_MODVERSIONS` 情形下也不可仅凭 vermagic 字符串差异断言一定加载失败。

## 下一步（先静态核对，不刷机）

1. 只读检查设备上原厂 `/proc/kallsyms` 的符号名称（**不收集内核地址**），或从精确版本原厂 boot 解包核对是否含额外 Qualcomm/Xiaomi 原厂导出；优先 `ipc_log_*`、`qcom_smem_*`、Rust Binder 导出。
2. 确认 `modules.load` 与运行时 vendor/system zram、zsmalloc 使用组合，排除混用。
3. 获取匹配 OS4.0.5.0 的原厂 boot.img、模块加载列表、签名/namespace/ABI 元数据，才能继续评估 R62 的定制方案。
4. 在确认关键缺失接口来源之前，**不要发布 AnyKernel3，不要实刷，不要把只编译成功的 BakaSU/SUSFS/NoMount 当作已兼容**。

源数据与逐模块报告保存在用户当前会话的分析文件中；GitHub 仅存结论，不包含上传的厂商 .ko、私人设备日志或任何内核地址。
